Talker LLM 选型：业界方案洞察（云侧 · 开源 vs 闭源 SOTA）

> 研究对象：语音交互系统 Talker 层内的 LLM，负责闭环简单任务——闲聊、查询、单步到两步工具调用。复杂推理与长任务交给 Thinker。

> 部署边界：只考虑云侧（自建 GPU 或云 API），不考虑端侧。

> 模型分两轨：开源轨用于实际选型；闭源 SOTA 轨用于摸高（探能力上限、量化差距）。

> 场景：家庭音箱 + 手机助手。

> 版本：v2.0　｜　日期：2026-11-03

> 来源分级：【官方】模型卡/厂商文档｜【榜单】公开榜｜【第三方】媒体/博客｜【自研归纳】

1. 结论摘要

#判断依据
1云侧开源已能覆盖 Talker 任务：9B–27B 一档是主力，百 B 级 MoE 才谈得上"接近闭源"Qwen3.5-9B BFCL-V4 66.1 / τ² 79.1【官方】；Qwen3.5-27B、122B-A10B 均为 Apache-2.0【官方】
2闭源 SOTA 的领先主要在多轮工具与长上下文，不在单轮查询BFCL v4 榜首 Overall 77.47、单轮 88.58、多轮 73.76【榜单】
3查询必须走工具，任何模型都不能靠参数知识小模型幻觉率 80–82%【第三方实测汇总】；闭源也一样，只是错得更少
4时延瓶颈是判停（200–800 ms）而不是 LLM（200–1000 ms）级联链路区间汇总【第三方】
5家庭音箱与手机助手的差异在声学与工具集，不在模型能力远场 vs 近场、家居控制 vs 跨应用，工具 schema 完全不同

一句话：这次选型是"在云侧开源里找最稳的一档，用闭源 SOTA 画一条上限线，看差距值不值得多花钱"。

2. 任务边界

能力归属判据
闲聊、情感回应、附和Talker无需外部信息，1 轮内可答
单步查询（天气/日程/音乐/百科/汇率）Talker1 次工具调用 + 转述

用法：只跑尺子1（公开集）+ 尺子2 的少量抽样，得到一条"上限线"。它的价值不是被选上，而是让选型结论有参照——例如"27B 开源做到上限的 92%，差 8 个点，值不值得多付 10 倍成本"。

4. 场景差异：家庭音箱 vs 手机助手

维度家庭音箱手机助手
声学远场 1–4 m、混响、电视干扰近场 0.2–0.5 m、街道噪声
交互唤醒后连续对话、多人共享单手、随时打断、屏幕上下文
工具集灯/空调/窗帘/扫地机/定时/音乐/家庭日程微信/日历/地图/音乐/通知摘要/打车
权限家庭共享，写操作要确认个人隐私，敏感操作要二次确认
失败代价全家人听到错误回复隐私泄露风险更高
典型 query"把客厅灯调暗一点""明早七点叫我""把刚才那条消息回个好的""导航到公司"

两条推论【自研归纳】：

  1. 两场景不能共用一套工具集评测，否则测的是模型对 schema 的泛化，不是业务能力。
  2. 家庭音箱的写操作比例更高（灯/空调/门锁），因此"误调"与"确认"权重应高于手机助手。

5. 时延预算（云侧）

段典型区间说明
入网与缓冲20–100 ms公网 RTT + 抖动缓冲
判停200–800 ms固定静音超时常见 500 ms
ASR 终稿100–500 ms流式分块
LLM 首 token200–1000 ms模型大小、prompt 长度、是否触发工具
TTS 首帧80–300 ms是否早发首句
出网与播放40–200 ms网络 + 端侧缓冲

云侧门槛（本文档采用）：

  • Talker LLM TTFT：P50 ≤ 500 ms、P95 ≤ 800 ms（含工具决策）
  • 一句话（≤25 字）整句时延：P95 ≤ 1.5 s

> 注意：这里说的是离开机房前的模型侧时延；端到端体感还要加上网络与 TTS，那部分由 L1/TTS 负责，不在本选型范围。

6. 能力证据：榜单能证明什么

6.1 BFCL v4 的结构（2026-04-12 版）

维度含义对应我们的任务
Single Turn（AST）函数名 + 参数单步查询
Multi Turn多轮工具交互两步闭环
Agentic（Web Search/Memory）检索与记忆编排我们不做，仅参考
Hallucination（Relevance/Irrelevance）该不该调"不该调时不乱调"
Latency（Mean/P95）端到端秒数唯一可直接用的时延数据

榜首：Overall 77.47、单轮 88.58、多轮 73.76、幻觉 79.79【榜单】。多轮只有七成多，这正是 Talker 需要重点测的切面。

6.2 开源 vs 闭源的差距在哪

切面差距量级【自研归纳】对选型的影响
单轮工具、参数填充小（个位数 pt）开源 9B–27B 基本够
多轮工具、并行调用明显（10 pt 量级）两步闭环要靠尺子2 实测
长上下文（>32k）明显Talker 用不到，可忽略
中文口语理解开源国产模型不落后家庭/手机场景反而占优
事实幻觉都在 80% 量级（AA-Omniscience）都别信参数知识，一律走工具

7. 业界五种做法（可借鉴）

模式做法对我们的用法
查询全工具化天气/音乐/日程全部走 API，模型只选工具与转述尺子2 的工具集照此设计
口语化后处理生成后去 markdown、限长、改数字读法进入评测（B 轴），不放在模型外
大小模型分工小模型出话、大模型兜底对应 Talker/Thinker；Talker 只需 9–27B 档
上限对照用闭源 SOTA 画一条线，判断差距是否值得付费本研究的"摸高轨"
门控前置先判该不该说话，再说内容已由 L1 承担

8. 对选型的五条启示

  1. 候选池只放可自部署的开源模型（9B / 27B / 122B-A10B / V4-Flash），闭源 SOTA 单列"摸高轨"。
  2. 尺子1 公开集负责淘汰与摸高，尺子2 业务集负责定选；公开集分数不能直接当业务结论。
  3. 两个场景两套工具集，家庭音箱偏写操作与确认，手机助手偏跨应用与隐私。
  4. "不该调"比"调错"更重要：语音场景里瞎调一次灯，用户会记很久。
  5. 时延自己压：榜单 Latency 列只做初筛，真实 P95 必须在自己的部署与量化上测。
