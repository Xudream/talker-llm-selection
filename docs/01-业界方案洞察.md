# Talker LLM 选型：业界方案洞察

> 研究对象：语音交互系统 Talker 层内的 LLM，负责**闭环简单任务**——闲聊、查询（天气/日程/音乐/百科）、单步到两步的工具调用；复杂推理与长任务交给 Thinker。
> 版本：v1.0　｜　日期：2026-11-03
> 来源分级：【官方】模型卡/厂商文档｜【榜单】公开榜实测｜【第三方】媒体/博客汇总｜【自研归纳】我的提炼

---

## 1. 结论摘要

| # | 判断 | 依据 |
|---|---|---|
| 1 | 端侧 4B 已经够"能用"，9B 是"好用"的分水岭 | Qwen3.5-9B BFCL-V4 66.1、τ²-bench 79.1【官方】；端侧三强是 Qwen3-4B-2507 / Gemma 4 E4B / Phi-4-mini【第三方】 |
| 2 | **查询类不能靠参数知识**，必须走工具 | Qwen3.5-4B/9B 在 AA-Omniscience 上幻觉率 80–82%【第三方实测汇总】 |
| 3 | 时延里 LLM 只占 200–1000 ms，且可以与判停重叠 | 级联链路实测区间【第三方】；判停 200–800 ms 往往比 LLM 更贵 |
| 4 | 口语化输出是**独立能力**，榜单完全不覆盖 | BFCL/τ² 只看工具正确性，不看"这句话能不能念出来" |
| 5 | 选型必须"部署形态先行"：端侧/边缘/云三档的候选池不同，跨档比较无意义 | 三档的量化、显存、成本结构完全不同 |

**一句话**：Talker LLM 的选型不是"找最强的 4B"，而是"在时延预算内，找工具调用最稳、口语最像人、事实不编的那一档"——这三件事公开榜单只覆盖第一件。

## 2. 先划清任务边界

| 能力 | 归属 | 判据 |
|---|---|---|
| 闲聊、情感回应、附和 | Talker | 无需外部信息，1 轮内可答 |
| 单步查询（天气/时间/日程/音乐/百科） | Talker | 1 次工具调用 + 转述 |
| 两步闭环（查完再控制，如"看看明天天气再决定要不要带伞"） | Talker（上限） | ≤2 次工具调用 |
| 多步规划、跨应用编排、长文分析 | Thinker | 需要分解、需要多轮观察 |
| 拒识 / 判"这话是不是对我说的" | L1 语义 VAD | 不进 Talker LLM（见 sidetalk-eval 研究） |

这条边界决定评测集的重心：**工具调用的"简单但高频"，不是"复杂但罕见"**。

## 3. 三档部署形态与候选池

### 3.1 端侧（手机 / 车机 / 眼镜，1–4B）

| 模型 | 参数 | 许可 | 上下文 | 工具调用 | 备注 |
|---|---|---|---|---|---|
| Qwen3.5-0.8B / 2B / 4B | 0.8 / 2 / 4B | Apache-2.0 | 262K | 原生 function calling | 原生多模态（含视觉），thinking/non-thinking 混合【官方】 |
| Gemma 4 E2B / E4B | 有效 2B / 4B | Gemma 许可 | — | 支持 function calling | **E2B/E4B 原生支持音频输入**【官方】 |
| Phi-4-mini-instruct | 3.8B | MIT | 128K | 支持 | 微软系，端侧老牌【官方】 |
| Qwen3-4B-Instruct-2507 | 4B | Apache-2.0 | 256K | 支持 | 2025 代，仍被端侧方案广泛采用【第三方】 |
| Llama 3.2 1B / 3B | 1 / 3B | Llama 许可 | 128K | 支持 | 生态最广，中文偏弱 |

端侧的现实约束（不是模型能力问题）：

- Q4_K_M 量化下 4B 约 2.5–3 GB 内存占用，手机可跑但会和相机/导航抢内存
- 冷启动加载 4B 约 1–3 s，**必须常驻或预热**，否则首轮体验崩
- 解码速度是硬约束：30 tok/s 时，一句 20 字的回复要 0.7 s 才念得完

### 3.2 边缘 / 单卡（4–9B，机房侧）

| 模型 | 参数 | 用途 | 关键数据 |
|---|---|---|---|
| **Qwen3.5-9B** | 9B | 边缘主力候选 | BFCL-V4 **66.1**、τ²-bench **79.1**、MMLU-Pro 82.5【官方】 |
| Qwen3.5-4B | 4B | 边缘低成本档 | Intelligence Index 27（<5B 最强）【第三方】 |
| Qwen3.5-2B | 2B | 降级/兜底 | Intelligence Index 16，追平 7B 级 Falcon-H1R【第三方】 |
| 其他 | — | 需按许可与中文能力单独评 | — |

9B 的价值不在"更聪明"，而在**工具调用成功率跨过 60% 线**——低于这条线，用户每 3 次就遇到 1 次失败，语音场景无法用"重试"掩盖。

### 3.3 云 API（Lite / Mini 档）

| 模型 | 输入 / 输出价格 | 上下文 | 备注 |
|---|---|---|---|
| Doubao Seed 2.0 Lite | $0.13 / $0.76 每 M | 256K | 支持函数调用与视觉【第三方】 |
| Doubao Seed 2.0 Mini | $0.06 / $0.56 每 M | 256K | 高并发批处理档【第三方】 |
| qwen-plus / qwen-flash | 国内按 token 计费 | 大 | 我们已实测：flash 300 ms、plus 460 ms 首包【实测】 |
| DeepSeek-V4-Flash | 低价档 | 大 | 适合做对照，不做主力 |
| Gemini Flash-Lite / GPT-mini 档 | — | — | 需出境评估，语音场景通常不选 |

云档的真实成本不在 token，而在**网络往返**：国内跨省 RTT 20–60 ms，加 TLS 与排队，首包很难稳定低于 300 ms。

## 4. 时延预算：LLM 到底能占多少

级联链路的六段实测区间【第三方汇总】：

| 段 | 典型区间 | 驱动因素 |
|---|---|---|
| 入网与缓冲 | 20–100 ms | 网络距离、抖动缓冲、编解码 |
| **判停（end-of-turn）** | **200–800 ms** | 静音超时或判停模型，固定 500 ms 很常见 |
| STT 终稿 | 100–500 ms | 流式分块、终稿逻辑 |
| **LLM 首 token** | **200–1000 ms** | 模型大小、prompt 长度、工具调用 |
| TTS 首帧 | 80–300 ms | 音色、是否早发首句 |
| 出网与播放 | 40–200 ms | 网络、端侧缓冲 |

两条推论【自研归纳】：

1. **LLM 不是瓶颈，判停才是**。把判停从 500 ms 固定超时改成预测式，收益和"把 9B 换 4B"相当，但不需要牺牲能力。
2. 人类轮转间隔约 200 ms（跨语言研究共识），系统不可能追平；但**首句 300 ms 内出声**能把体感拉回"可对话"。因此 Talker LLM 的门槛应定为：
   - 端侧：TTFT ≤ 300 ms（Q4 量化、1k 上下文、单并发）
   - 边缘/云：TTFT ≤ 500 ms，P95 ≤ 800 ms

## 5. 能力证据：榜单能证明什么、不能证明什么

### 5.1 BFCL v4 的评分结构（2026-04-12 版）

| 维度 | 含义 | 对我们的价值 |
|---|---|---|
| Single Turn（AST） | 单次调用的函数名与参数 | 对应"单步查询" |
| Multi Turn | 多轮工具交互 | 对应"两步闭环" |
| Agentic（Web Search / Memory） | 带检索、带记忆的编排 | 我们不做，仅参考 |
| Hallucination（Relevance/Irrelevance） | 该不该调、该不该拒 | 对应"不该调时不乱调" |
| Latency（Mean/P95，秒） | 端到端延迟 | 唯一可直接用的时延数据 |

榜首 Claude-Opus-4.5 Overall 77.47、单轮 88.58、多轮 73.76、幻觉 79.79【榜单】。**这个分数段说明：即便是最强模型，多轮工具也只有七成多。**

### 5.2 小模型的实际水位

| 模型 | BFCL-V4 | τ²-bench | 来源 |
|---|---:|---:|---|
| Qwen3.5-9B | 66.1 | 79.1 | 【官方】模型卡 |
| Qwen3.5-4B | 待实测 | 待实测 | — |
| Qwen3-4B-2507 / Gemma 4 E4B / Phi-4-mini | 三家差距明显，需自测 | — | 【第三方】博客明确声明"数字是范围估计，不是单机实测" |

**关键提醒**：第三方对比文自己也写了"these numbers are illustrative ranges"，所以候选池可以照它选，**分数不能照它抄**——必须自己跑。

### 5.3 幻觉是"查询"场景的头号风险

Qwen3.5-4B 在 AA-Omniscience 上幻觉率 80%、准确率 12.8%；9B 幻觉 82%、准确率 14.7%【第三方实测汇总】。

这条决定了产品设计：**Talker 的"查询"必须走工具/RAG，参数知识只能用于闲聊**。评测集必须包含"工具返回空/超时/无权限"三类分支，考察模型会不会拿参数知识硬编答案。

## 6. 业界怎么做的（模式提炼）

| 模式 | 代表做法 | 对我们的可借鉴点 |
|---|---|---|
| 端云混合 | 简单指令端侧、复杂转云 | Talker 端侧 4B + Thinker 云侧，正是这个形态 |
| 查询一律走工具 | 语音助手把天气/音乐/日程全部工具化，模型只负责选工具与转述 | 评测权重应向"工具选择 + 短转述"倾斜，而不是考模型知识 |
| 口语化后处理 | 生成后过一遍"去 markdown、限长、改数字读法" | 我们的 L3 已有约束层；Talker 同样需要，且要**进评测** |
| 双模型分工 | 小模型出话、大模型兜底 | 与我们 Talker/Thinker 分工同构 |
| 门控前置 | 先判"该不该说话"，再决定说什么 | 已由 L1 语义 VAD 承担，不重复建 |

【自研归纳】五条里，只有"查询走工具"和"口语化后处理"是 Talker LLM 选型能直接落地的两条；其余两条是架构层，一条在 L1。

---

## 7. 对选型的五条启示

1. **候选池按部署形态分三组**，不跨档比较：端侧 0.8–4B、边缘 4–9B、云 Lite。
2. **工具调用是主判据**，且分"单步 / 两步 / 不该调"三种切面；只有单步过关不够。
3. **口语约束必须自建**：首句 ≤15 字、禁 markdown/列表/括号、数字读法、不许复述用户原话。
4. **事实性用"数字与专名精确匹配"判**，不靠 judge；同时设"缺素材应说不知道"的负例。
5. **时延自己压**：TTFT/P95 在量化版本上测，榜单的 Latency 列只能做初筛。
